개발 설계

운영 규칙은 MVP 운영 정책, 알림 트리거·스케줄러는 알림 정책를 기준으로 합니다.

원본: src/assets/app.js, catalog.js, access.js, revenue.js. 영어는 tools/i18n/build_english.py로 생성한다. 기존 B-* ID와 localStorage 키는 내부 호환성을 위해 유지한다.

  • library: 공통 장소 보관함. trips/activeTripId: 여행별 저장과 선택 상태. board/days: 현재 여행의 날짜별 일정. 기존 단일 여행 데이터는 첫 여행으로 보존한다.
  • request: 공개 여행 스냅샷. requestType(itinerary/free), region, date/endDate, dayCount, days(날짜별 장소)를 포함하고 기존 요청은 하루로 호환한다. proposals: 메이트별 견적 배열. message: 금액 아래에서 입력하는 여행자 메시지(선택, 최대 1,000자). 여행자의 도착한 제안 카드와 제안 상세의 금액 아래에 표시하며 메이트의 보낸 제안에서도 확인한다. quote: 현재 상세 선택 제안.
  • booking: 선택 제안 스냅샷, feeRate=0.1, feeAmount, feeStatus, paymentMethod=cash, cashStatus.
  • 프로필·읽음 상태·닉네임 디렉터리는 현재 로컬 저장이다. 서버 인증·소유권·개인정보 보호는 별도 구현이다.

booking.feeDeadline과 bookingHistory는 결제 기한·이력을 보존한다. refundStatus는 접수·보완·승인·처리·완료·반환 제외를 구분한다. unavailableDates와 cashStatus는 이전 저장 호환용이며 휴무 달력·현금 수령 확인 기능으로 사용하지 않는다.

서버 연결 계약

여행자 예약 요청은 awaiting_mate_fee. PG 서버 응답·서명 웹훅의 금액/통화/주문/선택 메이트 ID를 대조한 후 confirmed. 클라이언트 성공 값만으로 확정 금지. 서버 가격 스냅샷·트랜잭션·결제 멱등성·취소와 결제 경합 보상 처리를 구현한다. 닉네임 canonical UNIQUE와 소유권 검사는 서버에서 원자적으로 수행한다.

상세 계약·미확정 사항

문의 접수와 Slack 알림 · MVP 개발 요건

2026-11-23 결정. 도움말의 직접 문의 작성에서 문의를 보내면 서버에 접수하고 운영팀 Slack 채널로 알린다. 사용자 흐름은 접수로 끝난다. 저장됨·처리 완료 전용 화면, 문의 이력, 저장 건수와 최근 상태는 제공하지 않는다. 처리 상태는 운영 웹에서만 관리한다.

  • 실서비스 버튼은 ‘문의 보내기’. 내용은 앞뒤 공백 제거 후 10~1,000자, 문의 유형은 허용 목록으로 서버에서 검증한다. 전송 중 중복 클릭을 막고 서버 접수 성공 시 ‘문의가 접수되었어요.’ 토스트를 잠시 보여준 뒤 빈 양식으로 돌아간다. 입력 오류·네트워크 오류·서버 오류는 내용을 유지하고 재시도를 허용한다.
  • 개발 API 계약: POST /api/support/tickets. 요청은 type, body, locale, 첨부 업로드 참조와 필요한 노쇼·지각 증빙 필드, 클라이언트가 생성한 Idempotency-Key다. 위치는 접수 시 사용자 동의 후 확인하며 실패 시 첨부로 대체한다. 서버는 첨부 소유권·형식·크기를 검증한다. userId와 역할은 서버 세션에서 결정한다. 서버는 문의와 Slack 알림 작업을 하나의 트랜잭션으로 저장하고 201 {ticketId, status: 'received'}를 반환한다. 같은 사용자·키·동일 내용 재요청은 기존 접수 결과를 반환하고, 같은 키의 다른 내용은 409로 거절한다. 동일 제출 재시도에는 같은 키를 유지한다.
  • Slack 전송은 서버 작업자가 담당한다. 서버 비밀 설정 SUPPORT_SLACK_WEBHOOK_URL로 운영팀이 지정한 채널에 전송하며 브라우저·소스 저장소에 웹훅 주소를 노출하지 않는다. 알림은 문의 ID, 유형, 접수 시각(Asia/Seoul), 권한 보호된 운영 문의 상세 링크로 구성한다. 문의 본문·연락처·위치·첨부는 Slack에 넣지 않는다. 사용자 입력은 일반 텍스트로 처리해 멘션 실행을 막고 인증 토큰·결제정보 등은 넣지 않는다.
  • 서버 접수와 Slack 전송 결과를 분리한다. Slack 장애가 나도 접수된 문의를 사용자에게 재제출시키지 않는다. 운영 웹에 알림 상태 pending/sent/failed와 재시도 횟수·마지막 오류를 표시한다. 일시 오류는 최초 이후 1분·5분·30분 간격으로 최대 3회 재시도하며 최종 실패는 운영 오류 목록에서 확인한다. 응답 유실로 접수 여부가 불명확하면 무조건 재전송하지 않는다. 문의 ID로 작업 중복을 방지하되 응답 유실 시 외부 알림 중복 가능성은 같은 문의 ID로 식별한다.
  • 운영 준비: 수신 워크스페이스·채널 확정, 웹훅 비밀 설정, 서버 인증·접수 DB·작업자·운영 상세 링크·요청 빈도 제한 구현. 실제 테스트 문의는 별도 승인 후 발송한다. Slack 알림은 운영 수신용이며 Slack 답글을 앱으로 전달하는 기능은 MVP 범위 밖이다.
  • 인수 기준: 정상 제출 1건 접수 및 Slack 수신, 한영 문의 원문 보존, 연속 클릭·응답 유실 후 동일 키 재시도의 중복 접수 방지, 입력 오류·접수 실패 시 본문 유지, Slack 장애 후 재전송, 새로고침·처리 완료 후에도 사용자 상태 화면 미노출을 확인한다.

현재 시제품은 ‘문의 저장’과 외부 전송이 없다는 토스트로 브라우저 저장만 시연한다. 실제 API·DB·Slack 연결은 미구현이다. 기존 tickets 저장 키와 운영 웹 문의 상태는 유지한다.

메이트 등록·승인

마이에서 메이트로 등록하기 → 전국 시·도 전체 또는 시·군·구 활동 지역 복수 선택(일반구가 있는 시는 구 단위, 제주는 제주시·서귀포시, 하위 시·군·구가 없는 세종은 전체)/영어·일본어·중국어·한국어 중 언어 1개 이상 복수 선택 → 필수 프로필 사진·직접 입력하는 활동 이름(사용자 닉네임과 메이트 활동 이름의 통합 중복 검사, 2~20자)·통합 자기소개(10~1,000자) → 비공개 안내 이메일 인증(인증된 계정 이메일 재사용)·휴대폰 번호·6자리 문자 인증 UI(시연용 123456, 실제 발송 없음, 유효시간 3분, 재전송 간격 30초, 5회 실패 제한) → 입력 확인·필수 동의 → 심사 요청. 활동 지역 선택은 하단 바텀시트로 제공하며 제목·시도 선택과 선택 요약·완료 버튼은 고정하고 지역 목록만 스크롤한다. 지역 버튼은 기본 4열, 360px 미만에서는 3열이며 내용을 약 90% 크기로 압축하고 최소 40px 터치 영역을 유지한다. 단계 진행률·이전·닫기·자동 임시 저장을 제공한다. 필수 사진은 JPG/PNG/WebP 1MB 이하로 미리보기·교체·삭제하며 브라우저에 저장한다. 동네와의 인연·걷는 속도/휴식·가능한 도움은 자기소개 한 영역에 자유롭게 작성하며 기존 개별 입력값은 빈 줄로 합쳐 보존한다. 관련 경험·자격 입력란은 제공하지 않는다. 공개 미리보기에는 본인 작성·미검증을 표시하고 연락처을 제외한다. 실제 운영의 확인 표시는 항목별 근거 종류·검토자·확인 일시와 유효기간 기록이 있어야 하며, 등록 승인 자체로 인증 배지를 부여하지 않는다. 여행 후기 작성·조회는 MVP에서 제외하며 완료 동행 표시는 실제 완료 예약에 근거한다. 시제품에는 확인 및 동행 기록 없음으로 표시한다. 자택 주소와 실제 증빙은 시제품에서 수집하지 않는다.

draft → pending → approved 또는 needs_info/rejected. 보완 요청과 거절은 사유 필수이며, 신청자는 수정 후 pending으로 재제출할 수 있다. 심사 중에는 제출 내용을 읽기만 가능하다. 여행자 마이의 등록 카드는 미등록·심사 중·승인 완료·보완 요청·승인 거절 상태별 안내를 표시한다. 심사 중에는 제출 내용 확인, 보완 요청·거절은 사유 확인과 수정 후 재제출로 연결한다. 승인 완료 카드는 메이트 모드로 전환해 여행 요청 화면으로 연결한다. 승인 후에만 메이트 모드 전환과 활동을 허용한다. 메이트 마이의 프로필 편집에서 사진·활동 이름·자기소개를, 활동 정보 수정에서 분야·복수 지역·언어를 변경한다. 수정 내용을 재심사하며 승인 시 반영하고 취소 시 폐기하며, 이름 변경은 중복 확인이 필요하다. 승인 상태와 비공개 연락처·심사 정보는 유지한다. 여행자 기능은 계속 이용 가능하다. 신청 시 결제하지 않으며 여행자 선택 후 10% 매칭 수수료 결제 → 예약 확정, 여행비 현장 현금 직접 지급 규칙을 유지한다.

운영 웹의 메이트 등록 심사에서 신청서·비공개 연락처을 검토하고 확인 체크 후 승인한다. 실제 운영에서는 본인 확인·자격 진위·계약 검증 기록이 있어야 승인 가능하다. 필요한 자격을 수동 확인하고 자료 접수 완료 후 3영업일 이내 심사 결과를 안내한다. 공개 프로필에는 연락처·증빙·심사 사유를 포함하지 않는다.

현재는 reeltrip-mate-application-v1에 하나의 시연 신청서를 저장하고 같은 출처·브라우저의 앱/운영 웹에서 공유한다. 한국어·영어 화면은 같은 신청서를 사용한다. 승인 상태를 기존 reeltrip-prototype-access-v1 권한에 반영한다. 활동 이름은 랜덤 부여하지 않으며 단계 진행과 제출 시 통합 목록을 재검사한다. 현재 중복 검사는 동일 브라우저의 시연 데이터에 한정되며 실서비스에서는 사용자 닉네임과 메이트 이름을 통합한 서버 고유 제약이 필요하다. 실제 사용자별 DB·인증·실제 SMS 발송 및 서버 검증·서류 업로드·알림·다중 사용자 처리는 미구현이다. 실제 승인 API는 관리자 권한·pending 상태·필수 검증·신청 버전을 서버에서 확인하고 역할 부여와 심사 로그를 원자적으로 저장해야 한다. 모든 메이트 활동 API는 서버에서 승인 상태를 검사해야 한다.

실서비스 요구사항: 선택한 날짜의 일정에 포함된 위치 확인 완료 장소는 모두 지도에 표시한다. 성수 3곳 뒤에 4번 N서울타워를 추가하면 남산까지 포함하도록 지도 범위를 자동 조절하고, 목록과 같은 4번 핀을 표시해야 한다.

현재 시제품에서 4번이 보이지 않는 이유

2026-11-23 확인. 화면 탐색의 기본 미리보기는 src/frontend/preview-map-config.js에서 review 모드로 설정한다. src/assets/app.js의 reviewMapImage()는 성수동 고정 지도 캡처 위에 핀을 겹쳐 그리며, reviewPosition()은 캡처 범위 밖 좌표를 null로 반환한다. N서울타워는 좌표가 있지만 남산에 있어 범위 밖으로 제외된다. 이는 ‘핀은 3개까지만 표시’라는 제품 정책이나 일정 추가 실패가 아니라 고정 이미지 미리보기의 한계다. 캡처 안에 임의로 4번 핀을 배치해서 해결하지 않는다.

실제 지도 구현 기준

  • 실제 지도에서는 선택 날짜의 전체 일정 좌표로 bounds를 계산한다. 최초 진입·날짜 전환·장소 추가/삭제 시 모든 핀이 보이도록 조정하며 헤더·일정 시트에 핀이 가리지 않도록 여백을 반영한다. 한 장소는 적정 확대 수준으로 중심 이동하고, 빈 일정은 빈 상태를 표시한다.
  • 목록의 방문 순서와 핀 번호를 동일하게 유지한다. 위치 미확인 장소를 제외하더라도 나머지 핀 번호를 다시 매기지 않는다. 순서 변경 시 번호도 함께 갱신한다.
  • 실제 지도 전환만으로 기존 예시 장소가 모두 표시되지는 않는다. 현재 pinEligible()은 Google placeId와 유효 좌표가 있고 demoCoordinates/demoPreview가 없는 장소만 허용한다. catalog.js의 N서울타워는 demoCoordinates:true인 예시다. 서비스에서는 실제 장소 검색·선택으로 위치를 확인한 데이터를 사용하고, 예시 플래그만 지워 위치 검증을 우회하지 않는다.
  • 좌표 누락·위치 미확인 장소는 일정 목록에 유지하고 ‘위치 확인 필요’ 안내와 장소 재선택 경로를 제공한다. 지도 연결 실패 시에도 목록을 유지하고 오류·재시도를 안내한다. 고정 이미지가 전체 장소를 표시하는 실제 지도인 것처럼 보이게 하지 않는다.
  • 직선 연결선은 방문 순서 표시이며 실제 도보 경로가 아니다. 실제 경로 데이터 연동 전에는 도보 경로로 안내하지 않는다.

인수 확인 항목

  • 실제 위치 확인을 마친 성수 3곳과 N서울타워로 일정 구성 → 지도에 1~4번이 모두 보이고 4번은 남산 위치에 표시된다.
  • 4번 추가/삭제, 순서 변경, 날짜 전환, 저장 후 재진입 → 현재 날짜 목록과 핀·번호·지도 범위가 일치한다.
  • 중간 장소의 좌표 누락 → 해당 목록 항목에 확인 안내가 보이며 이후 장소 번호가 당겨지지 않는다.
  • 장소 0개/1개, 지도 로딩 실패, 한국어/영어 및 모바일 일정 시트가 열린 상태를 확인한다.

이 항목은 개발 요구사항이며 현재 실제 지도 연동과 인수 검증을 완료했다는 의미가 아니다.

메이트 선택 해제와 자동 재모집

  • 확정 전 메이트 수동 거절 또는 수수료 결제 기한 만료 시 선택만 해제한다. 여행 시작 전이면 같은 요청 ID·일정·인원을 유지하며 자동으로 제안 모집을 재개한다.
  • 해제된 예약은 cancelled / feeStatus=void로 bookingHistory에 보존한다. 해당 메이트의 기존 제안은 만료시키고 booking·quote 및 요청의 선택 메이트 정보를 비운다. 다른 유효 제안이 있으면 request.status=quoted, 없으면 requested로 전환하며 새 제안을 받는다.
  • request.rematchReason=declined 또는 expired로 해제 사유와 재모집 안내를 표시한다. 다음 메이트를 선택하거나 여행자가 모집을 종료하면 안내를 해제한다. 취소된 선택에 대한 늦은 결제는 허용하지 않는다.
  • 여행 시작 시각 이후에는 자동 재모집하지 않고 일정 변경 후 새 요청을 안내한다. 여행자가 직접 예약 요청을 철회한 경우에는 자동 재모집하지 않고 시작 전 다른 제안 선택 버튼으로 재개할 수 있다. 제안 받기 종료와 확정 후 예약 취소도 자동 재모집하지 않는다.
  • 시제품 결제 기한은 선택 후 24시간과 출발 시각 중 빠른 시각이다. 앱 실행 중 타이머·화면 렌더링·결제 시 만료를 검사하며, 앱 종료 중 서버 작업·푸시·다중 사용자 동기화는 미연동이다. 실서비스에서는 서버 만료 작업과 PG 결제·거절 경합을 원자적으로 처리해야 한다.

검증 기준

node tools/tests/rematching_checks.cjs: 한국어·영어에서 수동 거절·기한 만료, 다른 제안 재선택, 유효 제안 없음과 새 제안 접수, 시작 시각 경과, 늦은 결제 차단, 저장 후 재진입을 확인한다.
