# 릴트립 알림 트리거와 발송 운영 정책

작성일: 2026-11-24

[알림 문서 열기](notification-policy.html)

홈페이지 MVP에서는 **상태가 바뀌면 알림을 만들고, 1분마다 실행하는 작업은 발송 시각이 된 건만 처리한다.** 1분마다 모든 사용자에게 알림을 보내는 방식이 아니다. 제안·채팅 이메일은 묶고, 결제·예약·취소는 지체 없이 처리한다.

이 문서는 구현할 운영 기준 제안이다. 주기·횟수·재시도 숫자는 MVP 기본값 제안이며 운영 데이터에 따라 조정한다. 현재 제공되는 것은 브라우저 알림 화면·읽음 표시·이메일 수신 설정 시연이다. 서버 이벤트 이력, 이메일 발송, 예약 작업은 아직 연결되지 않았다. 기존 문서의 푸시·30분 공개 여행 추천·후기 독촉 등 확장 제안은 이 MVP 기준으로 대체한다.

## 1 알림을 만드는 기본 원칙

- 버튼 클릭이나 화면 방문이 아니라 서버에서 성공적으로 저장된 사건을 트리거로 삼는다. 실패한 요청·취소·결제에는 완료 알림을 보내지 않는다.
- 여행자 선택은 예약 확정이 아니다. 메이트 수수료 10% 결제 성공을 서버에서 검증하고 예약을 확정한 뒤 확정 알림을 만든다. 여행비는 현장 현금 직접 지급이다.
- 현재 고객·메이트 모드와 관계없이 사건의 당사자에게 보낸다. 동일 계정이 양 역할에 포함되면 같은 사건을 중복 전달하지 않는다.
- 알림함은 사건별 이력을 남긴다. 현재 예약 상태만 보고 매번 새 알림을 생성하지 않는다. 읽은 알림도 유지한다.
- 즉시 알림함 기록과 이메일 발송을 분리한다. 이메일 실패 때문에 예약이나 알림함 기록을 되돌리지 않는다.
- 서버 시각은 UTC로 저장하고, 여행 시작·기한 및 문구는 한국 시간으로 계산·표시한다. 브라우저가 닫혀 있어도 서버 작업이 실행돼야 한다.

## 2 채널과 수신 설정

| 구분 | 알림함 또는 화면 | 이메일 기준 |
|---|---|---|
| 여행 소식 | 제안·선택·예약·취소·완료·심사 결과를 당사자에게 기록 | 여행 소식 이메일 ON인 계정만 발송 |
| 채팅 | 기존 채팅방과 읽지 않은 메시지 표시 사용 | 여행 소식 ON이고 아직 읽지 않은 경우에만 묶음 발송 |
| 인증 메일 | 사용자가 요청한 인증 흐름 | 알림 설정과 별개, 인증 시스템에서 발송 |
| CS 답변·자료 보완·반환 심사 결과 | 운영 웹 문의 기록. 사용자 문의 이력·처리 상태 화면 없음 | 사용자가 요청한 문의·반환 절차의 개별 답변으로 발송. 여행 소식 설정과 별개이며 광고를 섞지 않음 |
| 이벤트·혜택 | MVP에서는 자동 캠페인 미운영 | 광고 이메일 동의가 있는 경우에만 운영자가 승인한 캠페인으로 별도 발송 |
| 운영팀 | 운영 웹 업무 목록 | 일반 사용자 이메일과 분리. Slack은 새 CS 접수 알림 전용 |

가입 방법 선택 화면에는 체크박스가 없다. 이메일 가입 화면에만 광고 수신 선택 동의를 기본 미선택으로 두고 인증 성공 시 저장한다. 소셜 신규 가입은 광고 OFF이며 이메일 가입 중의 선택값을 이어받지 않는다. 로그인은 기존 동의를 변경하지 않는다.

마이 → 설정 → 알림 설정은 여행 소식 이메일(기본 ON), 이벤트·혜택 이메일(기본 OFF) 두 항목만 둔다. 이메일을 꺼도 알림함은 남고, OFF 이후 대기 중인 해당 이메일은 취소한다. 다시 ON으로 바꿔도 과거 알림을 일괄 발송하지 않는다. 발송 서비스에 이미 전달된 메일은 회수할 수 없다.

모든 이메일은 검증된 주소가 있을 때만 발송한다. 소셜 계정에 검증된 이메일이 없으면 알림함만 제공하고 발송 상태를 `skipped_no_verified_email`로 남긴다. 한국어·영어는 계정 언어로 문구를 선택하며 언어별로 같은 사건을 두 번 보내지 않는다.

## 3 이벤트별 발송 기준

표의 이메일은 별도 표시가 없으면 여행 소식 이메일 설정을 따른다. 알림함에는 사건 즉시 기록하고, 이메일의 즉시는 첫 발송 시도까지 정상 운영 시 1분 이내를 목표로 한다. 수신함 도착 시간을 보장하는 의미는 아니다.

| 사건과 트리거 | 수신자 | 알림 문구 예시 | 이메일 시점과 제한 | 눌렀을 때 |
|---|---|---|---|---|
| 새 제안이 유효한 공개 요청에 저장됨 | 요청한 여행자 | 메이트의 제안이 도착했어요 | 첫 미통지 제안부터 5분 뒤 해당 요청의 새 제안을 1건으로 묶음. 그 사이 확인한 제안·철회·만료 제안 제외 | 해당 요청의 도착한 제안 |
| 여행자의 선택과 결제 대기 예약 생성이 함께 성공함 | 선택된 메이트 | 여행자가 제안을 선택했어요. 11월 25일 오후 1시까지 예약을 확정해 주세요 | 즉시 1회. 실제 수수료·결제 기한 표시 | 해당 예약 수수료 화면 |
| 동일한 메이트 선택 사건 | 선택한 여행자 | 메이트의 예약 확정을 기다리고 있어요 | 본인이 수행한 선택이므로 이메일 생략, 알림함만 기록 | 예약 진행 상태 |
| PG 성공 검증 후 예약 확정 저장 | 여행자와 메이트 | 예약이 확정됐어요 | 각 1회 즉시. 메이트의 결제 완료와 예약 확정을 하나로 통합 | 확정 예약 상세 |
| 메이트 진행 거절 또는 결제 기한 만료 후 선택 해제 저장 | 여행자와 해당 메이트 | 메이트 선택이 해제됐어요 | 각 1회 즉시. 직접 거절한 메이트에게는 이메일 생략. 시작 전 재모집과 시작 후 모집 종료 문구 구분 | 해당 요청의 현재 상태 |
| 선택 전 제안 철회·다른 메이트 확정·공개 요청 철회 | 해당 제안을 보낸 메이트 또는 받은 여행자 | 제안이 종료됐어요 | 이메일 생략. 알림함에서 종료 사유 확인. 원래 제안 알림은 삭제하지 않고 현재 상태로 연결 | 제안 결과 |
| 확정 예약의 상대 메시지가 서버에 저장됨 | 상대방 | 아직 읽지 않은 메시지가 있어요 | 첫 미읽음부터 5분 뒤 확인. 대화방·수신자별 최대 30분에 1회. 채팅 알림함 항목은 메시지마다 추가하지 않음 | 해당 채팅방 |
| 예약 취소가 서버에서 확정됨 | 여행자와 메이트 | 예약이 취소됐어요 | 상대방에게 즉시 1회. 본인 취소는 화면·알림함으로 안내. 운영팀 취소는 양쪽에 발송 | 해당 예약 취소 결과 |
| 운영팀이 실제 PG 반환 성공 확인 후 완료 기록 저장 | 수수료를 낸 메이트 | 수수료 24,000원 반환이 완료됐어요 | 개별 반환 처리 결과 이메일 1회. 승인·접수 단계에서 완료로 보내지 않음 | 수수료 반환 내역 또는 이메일 회신 안내 |
| 운영팀이 메이트 심사·재심사 결과 저장 | 신청한 메이트 | 메이트 등록이 승인됐어요 / 신청 내용을 보완해 주세요 | 결과 버전마다 1회 즉시. 반려·보완은 사유 포함 | 본인 신청 결과 |
| 운영팀이 활동 제한을 확정 | 해당 메이트 | 메이트 활동이 제한됐어요 | 사유와 회신 안내를 개별 처리 결과 이메일로 1회. 신고 접수만으로 생성하지 않음 | 제한 상태·문의 안내 |
| 여행 완료 상태가 저장됨 | 여행자와 메이트 | 함께한 여행이 완료됐어요 | 이메일 생략, 알림함만 기록. 후기 독촉은 MVP 제외 | 완료 여행 |
| 운영자가 문의 답변·자료 보완 요청을 저장 | 문의한 사용자 | 남겨주신 문의에 대한 답변입니다 | 답변 버전마다 1회 개별 이메일. 사용자 알림함에 문의 상세 링크를 만들지 않음. 폼 작성 중·내부 메모에는 발송하지 않음 | 이메일 본문과 회신 안내 |
| 새 문의·신고·노쇼·반환 요청 접수가 저장됨 | 운영팀 | 새 문의가 접수됐어요 | 운영 웹 목록과 새 접수 Slack 1회. 대기 상태라는 이유로 반복 전송하지 않음 | 운영 웹 접수 상세 |

결제 실패는 결제 화면에서 재시도를 안내하고 실패 이메일은 보내지 않는다. 결제 성공 여부가 불명확하면 실패나 확정으로 추정하지 않고 운영 확인 대상으로 남긴다. 날짜·인원 변경은 기존 정책대로 취소 후 새 요청이며 별도의 일정 변경 알림을 만들지 않는다. 채팅에서 합의한 만남 정보도 자동으로 추출해 알림을 만들지 않는다.

## 4 예약 알림은 두 종류만 운영

| 예약 알림 | 생성 시점 | 발송 예정 시각 | 수신자와 횟수 | 발송 직전 조건 |
|---|---|---|---|---|
| 수수료 결제 마감 안내 | 여행자가 메이트를 선택했을 때 | 고정된 결제 기한 1시간 전 | 해당 메이트, 알림함·설정에 따른 이메일 각 1회 | 해당 선택이 유지되고 결제 대기이며, 기한과 여행 시작 시각이 지나지 않음 |
| 여행 전날 안내 | 예약이 확정됐을 때 | 예약 첫날 시작 시각 24시간 전 | 여행자·메이트, 알림함·설정에 따른 이메일 각 1회 | 해당 예약이 여전히 확정 상태이며 시작 전임 |

수수료 기한은 **메이트 선택 시각 + 24시간과 예약 첫날 시작 시각 중 빠른 시각**으로 고정한다. 페이지 방문 시 연장하지 않는다. 기한 만료 처리는 알림 발송 성공 여부와 무관하게 진행한다.

선택 시 이미 결제 기한까지 1시간 이하라면 별도 마감 알림을 만들지 않고 선택 알림에 정확한 남은 기한을 표시한다. 확정 시 첫날 시작까지 24시간 이하라면 전날 안내를 뒤늦게 발송하지 않고 확정 알림에 여행 준비 내용을 포함한다.

여러 날 여행도 첫날 기준 1회만 보낸다. 2시간 전 안내·매일 안내·제안 만료 독촉·미결제 반복 독촉은 MVP에서 제외한다. 전날 안내에는 날짜·인원·예약 상세 링크와 여행비 현장 현금 직접 지급을 넣는다. 만남 장소가 구조화된 확정 정보로 없으면 지어내지 않고 채팅에서 확인하도록 안내한다.

## 5 스케줄러 실행 주기

초기에는 DB 대기 작업 테이블과 **1분 주기 서버 작업 하나**로 시작한다. 별도 메시지 브로커나 사용자별 타이머는 필수가 아니다. 한 실행 안에서 만료 처리 → 예약 알림 생성 → 발송 대상 확보 순으로 진행한다. 발송량이 늘면 발송 작업자만 분리한다.

| 작업 | 실행 주기 | 실제 처리 조건 | 사용자에게 보내는 횟수 |
|---|---|---|---|
| 결제 대기 만료 | 매 1분 | 결제 기한이 지났고 아직 대기 상태. 서버에서 원자적으로 상태 변경 | 실제 만료 사건당 1회 |
| 예약 알림 처리 | 매 1분 | 예정 시각 이하이고 아직 처리되지 않은 예약 알림 | 예약·종류·수신자별 1회 |
| 제안 묶음 이메일 | 매 1분 | 최초 미통지 제안으로부터 5분 경과, 유효한 미확인 제안이 남음 | 해당 5분 묶음당 1회, 새 제안이 없으면 0회 |
| 미읽음 채팅 이메일 | 매 1분 | 미읽음 5분 경과 및 직전 발송 후 30분 경과 | 대화방·수신자별 30분에 최대 1회, 새 메시지가 있어야 추가 발송 |
| 즉시 이메일·재시도 | 매 1분 | 발송 예정 시각 도래, 발송 전 상태·설정 검증 통과 | 사건당 성공 1회, 일시 실패만 제한 재시도 |
| 운영 누락 점검 | 매일 오전 9시 한국 시간 | 최종 실패·처리 중 멈춤·누락된 예약 작업 점검 | 자동 사용자 재발송 없음. 운영 웹에서 확인 |

정상 운영의 발송 시각 오차 목표는 약 1분이다. 서버 지연·제공사 장애는 별도로 측정한다. 각 조회는 `due_at <= now`를 사용하며 특정 분과 정확히 같을 때만 처리하지 않는다. 미처리 작업을 오래된 순으로 한 번에 최대 100건 확보하고, 겹쳐 실행된 작업이 같은 행을 가져가지 못하게 잠근다. 1분 안에 처리량을 감당하지 못하면 대기 시간 경보를 내고 처리량을 확장한다.

## 6 묶음과 읽음 처리

제안 이메일은 요청·수신자 단위로 묶는다. 오전 10:00, 10:02, 10:04의 새 제안은 10:05 이후 한 번에 “새 제안 3개”로 안내한다. 수신자가 그 전에 확인했거나 제안이 종료됐다면 제외한다. 10:06의 새 제안은 다음 묶음으로 처리한다. 알림함의 개별 제안 기록은 즉시 남긴다.

채팅 이메일에는 상대 이름과 예약 식별 정보만 넣고 메시지 본문·연락처는 넣지 않는다. 10:00 메시지는 10:05까지 읽지 않으면 이메일 대상이 된다. 10:03에 읽으면 취소한다. 10:05에 보낸 뒤 새 메시지가 10:10에 오면 다음 발송 가능 시각은 10:35다. 새 메시지가 없으면 같은 미읽음 메시지를 30분마다 재전송하지 않는다.

열려 있는 탭이 있다는 이유만으로 읽음으로 보지 않는다. 해당 제안 또는 채팅의 읽음 위치가 서버에 반영됐는지 확인한다. 읽음과 발송이 동시에 발생하면 발송 직전 재검사까지 적용하고, 이미 제공사에 전달된 메일은 회수하지 않는다. 이메일 열람만으로 홈페이지 알림을 읽음 처리하지 않는다.

## 7 취소와 오래된 알림 처리

- 결제 성공·거절·기한 만료·여행자 취소가 확정되면 해당 결제 마감 작업을 취소한다.
- 예약 취소·완료가 확정되면 여행 전날 안내와 해당 예약의 대기 중 제안·채팅 이메일을 취소한다. 채팅이 마지막 날 자정에 닫혀도 대기 중 채팅 이메일을 취소한다.
- 설정 OFF·탈퇴·검증 이메일 상실 시 해당 수신자의 아직 보내지 않은 이메일을 취소한다. 법정 보존과 발송 가능한 활성 계정 여부는 별도 관리한다.
- 발송 직전에 수신자, 사건 버전, 현재 상태, 권한, 수신 설정과 검증 주소를 다시 조회한다. 오래된 결제 링크나 취소된 예약의 확정 안내를 그대로 보내지 않는다.
- 예약 리마인더가 예정 시각보다 30분 넘게 밀리면 폐기한다. 결제 기한·여행 시작 시각이 먼저 오면 그 시각에 폐기한다. 장애 복구 후 지난 전날 안내를 몰아서 보내지 않는다.
- 제안·채팅 메일은 원본 사건부터 최대 24시간, 또한 제안 만료·예약 종료 중 먼저 오는 시각까지만 유효하다. 일반 거래 이메일은 사건 후 24시간까지만 자동 재시도한다. 개별 CS 답변은 최대 72시간으로 두고 실패는 운영팀이 확인한다.
- 알림함의 과거 기록은 남기되, 눌렀을 때는 현재 상태로 연결한다. 권한이 없거나 기록을 더 이상 볼 수 없으면 목록과 안내를 제공하고 다른 사용자의 기록을 보여주지 않는다.

## 8 중복 방지와 재시도

서버의 상태 변경과 발송 대기 이벤트 기록은 같은 DB 트랜잭션으로 저장한다. 이렇게 해야 예약만 확정되고 알림 사건이 빠지는 경우를 줄일 수 있다. PG 웹훅 중복 수신, 작업 중복 실행, 재시도가 새 알림을 추가하지 않도록 DB 고유 제약을 둔다.

| 항목 | MVP 기준 |
|---|---|
| 이벤트 중복 키 | 사건 ID + 수신자 ID + 채널 + 알림 종류 |
| 예약 알림 중복 키 | 예약 ID + 해당 선택 또는 예약 버전 + 알림 종류 + 수신자 ID + 채널 |
| 제안·채팅 묶음 | 요청 또는 대화방 + 수신자 + 묶음 ID. 포함한 제안·메시지 범위 기록 |
| 일시 오류 | 최초 시도 후 1분, 5분, 30분 간격으로 최대 3회 재시도, 최초 포함 최대 4회 |
| 재시도 중 상태 변경 | 매 시도 직전 다시 확인하고 무효 작업 취소. 유효기간이 지나면 남은 횟수가 있어도 중단 |
| 영구 오류 | 잘못된 주소·수신 거부·반송 확정은 재시도 중단, 계정 이메일 상태와 운영 실패 목록 반영 |
| 전송 결과 불명 | 타임아웃 때 새 발송 키를 만들지 않음. 제공사 메시지 ID·중복 방지 키로 조회·재사용. 확인 불가면 운영 확인으로 전환 |
| 처리 중 작업 회수 | 처리 임대 5분 만료 후 복구. 제공사 접수 여부 확인 후 재개하며 무조건 재전송하지 않음 |
| 완료 기준 | 제공사 접수와 실제 배달을 구분해 기록. 제공사 접수 성공을 사용자의 열람 완료로 표시하지 않음 |

운영 재발송도 같은 사건의 발송 이력에 추가하고 사유·운영자·시각을 남긴다. 무조건 여러 번 보내는 버튼은 제공하지 않는다. 사용자별 전역 발송 제한으로 예약 취소 등 중요한 사건을 조용히 버리지 않고, 제안·채팅 같은 고빈도 종류만 묶음 제한을 적용한다.

## 9 운영 알림과 광고 범위

새 CS 접수는 Slack에 접수 번호·유형·운영 상세 링크만 보내고 전화번호·위치·첨부 파일·문의 본문은 넣지 않는다. 노쇼·여행 직전 취소 등은 운영 목록에서 우선순위를 높인다. Slack은 새 접수 전용이므로 일반 미처리 업무 독촉이나 마케팅 알림을 섞지 않는다. 발송 실패·PG 상태 불일치는 운영 웹 오류 목록에서 확인하며 접수 목록과 구분한다.

MVP는 광고 동의만 저장하고 자동 광고 발송·재방문 유도·추천 캠페인은 구현하지 않는다. 추후 운영 캠페인을 켠다면 승인된 캠페인마다 수신자별 1회, 전체 캠페인 합계 주 1회 이하, 한국 시간 평일 10:00~18:00로 제한하는 것을 기본안으로 한다. 발송 시점의 광고 동의와 검증 주소를 확인하고 철회자는 제외한다. 서비스 알림에 이벤트·할인을 끼워 넣지 않는다. 이는 운영 제안이며 별도 법률 요건 검토를 대체하지 않는다.

## 10 MVP에서 보내지 않는 알림

새 공개 여행 전체 메이트 일괄 발송, 30분마다 추천 여행, 제안 만료 2시간 전 독촉, 여행 2시간 전 추가 안내, 후기 요청, 장기 미접속·미완성 일정 독촉, 단순 조회·저장 성공, 반복 결제 실패 이메일은 제외한다. 공개 여행은 메이트가 홈페이지 목록에서 직접 찾는다. 앱 푸시·브라우저 푸시·SMS·사용자별 조용한 시간도 제외한다.

서비스·인증·개별 CS 이메일은 MVP에서 별도의 야간 지연 없이 처리한다. 광고는 위 운영 시간에만 발송한다. 일반 알림에 야간 무음 기능이 있는 것처럼 안내하지 않는다.

## 11 개발 기록과 검수 시나리오

기록 항목은 사건 ID·유형·관련 요청/예약/대화 ID·상태 버전·수신자·채널·언어·발생 시각·예정 시각·유효 기한·중복 키·발송 상태·시도 횟수·제공사 메시지 ID·읽음 시각·취소/실패 사유다. 설정은 계정별 수신 여부와 동의·철회 시각, 문구 버전, 출처를 서버에 기록한다. 현재 `reeltrip-notification-preferences-v1`은 브라우저 시연 저장이며 서버 동의 이력을 대체하지 않는다. 보존 기간과 개인정보 삭제 기준은 출시 전 별도 확정한다.

| 검수 상황 | 기대 결과 |
|---|---|
| 같은 PG 성공 웹훅 3회 수신 | 예약 확정 1회, 각 당사자 알림함·이메일도 1회 |
| 1분 작업 두 개 동시 실행 | 같은 작업을 하나만 확보하여 중복 발송 방지 |
| 여행자 선택 후 40분 뒤 결제 기한 | 선택 알림만 발송, 1시간 전 안내는 만들지 않음 |
| 여행 시작 20시간 전에 예약 확정 | 확정 안내만 발송, 지난 전날 안내 생략 |
| 결제 마감 안내 직전 결제 성공 | 마감 안내 취소, 확정 알림만 발송 |
| 결제 성공과 만료 작업이 경합 | 서버 결제 시각·예약 잠금 기준으로 한 결과만 확정. 불일치는 운영 확인, 상반된 알림 금지 |
| 제안 3개 중 2개를 확인하고 1개 철회 | 묶음 이메일 없음 |
| 채팅을 5분 안에 읽음 | 채팅 이메일 없음 |
| 30분 지나도 새 메시지가 없음 | 같은 미읽음 내용을 반복 발송하지 않음 |
| 이메일 OFF 후 대기 작업 실행 | 알림함 유지, 해당 이메일 취소 |
| 서버가 2시간 멈췄다가 복구 | 지난 리마인더 폐기, 유효한 작업만 재개. 과거 메일 일괄 폭주 금지 |
| 소셜 신규 가입·검증 이메일 없음 | 광고 OFF, 알림함만 사용, 주소를 임의 추정하지 않음 |
| 취소 완료 후 과거 확정 알림 클릭 | 취소된 현재 예약 상태 표시, 결제·채팅 재개 금지 |

운영 지표는 예정 시각 대비 최초 시도 지연, 중복 차단 건수, 유형별 발송·취소·실패 건수, 반송률이다. 즉시 작업이 5분 이상 밀리거나 최종 실패가 생기면 운영 오류 목록에 표시한다. 초기 기준으로 발송량과 실패를 관찰한 뒤 묶음 간격과 처리량만 조정한다.


## 11 메시지별 문구 전체

아래 제목·본문은 운영 구현용 문구 초안입니다. 알림함은 제목·본문·발생 날짜를 표시하며, 이메일은 같은 제목·본문에 해당 상세 화면 링크를 붙입니다. 이메일 전용·문의 기록·운영팀 메시지는 문구 비교를 위해 같은 카드 형태로 보여 주며 사용자 알림함에 새 항목을 추가한다는 의미는 아닙니다. 이메일 수신 설정·묶음·본인 행동 제외 조건은 위 발송 기준을 그대로 적용합니다. 이벤트·혜택 캠페인은 MVP에서 운영하지 않아 발송 문구를 정의하지 않습니다.

중괄호 변수는 저장된 사건의 실제 값으로 치환합니다. 여행일은 예약의 전체 날짜 범위, 시작시간은 첫날 시작 시각, 결제기한·인증기한은 연월일·시각·한국 시간 표기를 포함합니다. 사유는 사용자에게 공개 가능한 운영 확정 내용만 사용하고, 알 수 없는 값이나 만남 장소는 추정하지 않습니다. 카드 날짜는 발송일이 아닌 사건 발생일이며 아래 미리보기 날짜·이름·금액은 예시입니다.

| 상황 | 수신자 | 채널 | 제목 | 본문 | 연결 화면 |
|---|---|---|---|---|---|
| 제안 도착 | 여행자 | 알림함 | 메이트의 제안이 도착했어요 | 여행일 {여행일} · {메이트명} 님의 제안을 확인해 보세요. | 도착한 제안 |
