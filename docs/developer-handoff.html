개발 인계 · 앱 모드와 운영 웹

2026-11-17 사용자 결정. 현재 서비스 기준. 기존 모바일 공통 설명보다 이 문서의 플랫폼·권한 구분을 우선한다.

제품 구조

  • 고객/가이드: 동일 계정과 동일 모바일 앱. 고객 모드에서 여행 계획·요청·예약. 승인된 가이드는 가이드 모드에서 업무 수행.
  • 운영: 별도 웹 콘솔. 데스크톱 사이드 메뉴 및 넓은 콘텐츠 영역. 모바일 앱 내 모드 전환 대상이 아니다.

모바일 내비게이션

홈은 본문 상단의 작은 로고를 사용한다. 고객·가이드의 주요 탭은 별도 탑바 없이 본문 제목부터 시작한다. 상세 화면은 뒤로가기와 짧은 제목을 유지한다. 언어·계정·모드 전환은 두 모드가 공유하는 마이에 모은다. 도움말·이용 안내도 두 모드에서 접근할 수 있다. 운영 웹 헤더는 유지한다.

프로토타입 실행

  1. 모바일 앱 검토 도구를 열고 상단 검토 도구를 펼친다.
  2. 시연 계정 권한에서 승인된 가이드를 선택한다. 하단 마이 → 앱 설정에서 가이드로 전환 / 여행자로 전환한다.
  3. 일반 고객·심사 중·정지로 바꾸면 가이드 모드 버튼이 사라지고 고객 모드로 복귀한다. 가이드 hash 직접 접근은 안내 화면으로 차단한다.
  4. 데모 상태에서 요청/견적/예약을 준비해 고객·가이드 관점으로 확인한다. 데모 상태 불러오기는 기존 체험 데이터를 교체한다.
  5. 별도 운영 웹에서 장소·문의·심사·환불을 확인한다. 현재 운영자는 시연 계정이며 로그인하지 않는다.

개발 구현 계약

  • 서버가 userId, roles, guideStatus, 운영 permission을 반환한다. 클라이언트 mode는 UI 선호값일 뿐 권한 근거가 아니다.
  • 모드 전환은 로그아웃·데이터 초기화 없이 수행한다. 고객 데이터는 소유자, 가이드 데이터는 배정된 가이드 ID, 운영 데이터는 담당 권한으로 API에서 필터링한다.
  • 자격 정지·세션 만료 시 서버가 접근을 거절하고 앱은 고객 모드 또는 로그인으로 복귀한다. 작성 중 견적 보존/폐기 정책을 정의한다.
  • 운영 웹은 별도 세션·서버 인가·민감 작업 승인·감사 로그를 구현한다. 주소 분리나 프런트 라우트 가드는 보안 경계가 아니다.
  • 고객/가이드의 동일 예약 연결은 서버 ID 기준. 본 시연은 같은 origin의 localStorage 공유로만 표현하며 다기기 동기화는 없다.

행동 중심 화면 원칙

홈은 링크 입력 → 장소 찾기를 첫 행동으로 제공한다. 직접 추가·가이드 찾기·샘플 체험을 보조 경로로 두고, 진행 중인 예약·요청·저장 일정은 이어서 진행한다. 내 여행은 상태 확인과 일정 편집을 먼저 배치하고 전체 일정은 펼쳐서 확인한다. 가이드 홈은 요청 처리를 먼저, 업무 요약은 펼침 영역에 배치한다. 고객·가이드의 주요 화면에서 체험·시연·로컬 저장 안내는 제거하고, 금액·포함/별도 비용·취소 조건과 필수 동의는 해당 단계에 유지한다. 이는 화면 문구 정리이며 실제 API 연동 범위는 달라지지 않는다. 스타일은 assets/action-first.css, 번역은 i18n/action-first-translations.json에서 관리한다.

여행 메이트 명칭

고객 노출 명칭은 메이트, 주요 행동은 여행 메이트 찾기, 받은 견적은 도착한 제안, 요청 내용은 어떤 도움이 필요하세요?, 발행 행동은 함께할 여행 제안하기로 통일한다. 내부 guide 역할·경로·상태 키는 호환성을 위해 유지한다. 유료 제공 범위와 자격 검토 기준은 명칭 변경과 별개로 기존 인계 사항을 따른다.

여행 공개형 가이드 매칭

확정 흐름: 내 장소(영상·수동 추가) → 내 여행(장소를 날짜별로 구성) → 가이드 탭에서 여행 공개 → 여러 가이드가 일정과 견적 발행 → 고객이 비교·선택 → 선택 견적 확인 후 예약. 특정 가이드 지정 요청을 기본 흐름에서 제거했다.

library는 장소 보관함 ID, board/days는 날짜별 일정이다. 기존 보관함은 현재 일정에서 이동 없이 초기화하며 저장 키는 유지한다. proposals는 가이드별 견적 배열, quote는 현재 상세에서 선택한 견적이다. 기존 단일 quote는 proposals로 마이그레이션한다. 같은 가이드 재발행만 교체하고 경쟁 견적은 보존한다. 요청 마감 시 새 제안·견적 수락을 차단한다.

시제품은 1개 여행·1개 공개 요청을 유지하며 선택한 하루만 공개한다. 복수 여행·다수 고객 요청함, 서버 배포·알림, 가이드별 인증과 접근 범위, 실시간 견적 이력·예약 잠금은 후속 개발 대상이다. 비교용 두 견적은 기존 검토 도구에서만 생성한다. 견적 발신 계정 선택은 검토용이며 실서비스 발신자는 서버 인증에서 결정해야 한다. 기존 한영 로컬 저장은 독립적이며 서버 다기기 동기화는 없다.

알림

B-31 notifications: 평면 목록과 전체·여행 일정·가이드 유형 필터를 제공한다. 읽지 않은 알림 제목 왼쪽에 파란 점을 표시한다. 읽지 않은 알림은 진한 제목(700)과 기본 배경, 읽은 알림은 보통 굵기(400)와 기본 배경으로 구분한다. 여행 일정은 장소 분석 완료·일정 변경 소식, 가이드는 요청 응답·제안·메시지와 예약 확정·취소·후기 안내를 묶는다. 현재 이벤트는 요청/견적/예약만 생성하며 일정·메시지·후기 이벤트 수신은 후속 구현 대상이다. 필터별 데이터가 없으면 빈 상태를 표시한다. 고객 홈 우측 종 아이콘, 가이드 요청함 우측 종 아이콘으로 진입한다. 현재 요청 또는 예약 상태를 알림 카드로 표시하고, 상태·견적 버전 변경 시 읽지 않은 알림으로 표시한다. 개별 알림 클릭과 모두 읽음을 지원하며 모드별 읽음 ID를 기존 로컬 상태에 저장한다. 고객은 해당 요청/예약 상세, 가이드는 요청함으로 이동한다. 현재 상태 기반이며 과거 알림 이력·푸시·서버 수신은 구현되지 않았다.

도착한 제안 목록

메이트 탭의 도착한 제안은 요청한 여행 단위의 목록이다. 제안 받는 중/마감된 요청을 분리하고 요청 카드의 여행명·날짜·인원·장소 수·제안 수를 표시한다. 카드를 누르면 기존 requested에서 메이트별 제안을 비교한다. viewedProposals에 제안 ID+버전을 보관해 새 제안 수를 표시한다. 기존 1개 요청 모델을 유지하며 복수 요청 이력은 서버 및 다중 요청 모델의 후속 범위다.

확정 결제 정책 · 2026-11-17

이 항목이 과거 20% 수수료·플랫폼 여행비 수납/정산/환불 정책보다 우선한다. 여행자 제안 선택 → 예약 요청(awaiting_mate_fee) → 선택된 메이트가 약속 금액의 10% 매칭 수수료 선결제 → 예약 confirmed. 여행자는 현장에서 약속한 여행 비용 전액을 메이트에게 현금 지급한다. 플랫폼은 매칭만 제공하며 여행비를 수납·정산·송금하지 않는다.

금액은 예약 요청 시 선택 제안에서 스냅샷으로 고정한다. 매칭 수수료는 원 단위 반올림 amount×0.10. 여행자에게 별도 수수료를 청구하거나 현금 금액에서 수수료를 빼지 않는다. 여행비 240,000원일 때 메이트 선결제 24,000원, 현장 현금 240,000원이다. 현금 수령은 예약 확정·여행 완료와 별개이며 자동 수령 완료 처리하지 않는다.

실서비스는 선택된 메이트 user_id와 예약 ID를 검증하고, PG 서버 응답/서명 검증 웹훅의 금액·통화·주문 ID를 대조해야 한다. 프런트 성공 값으로 확정 금지. payment_id 고유성·멱등성, 예약 잠금, 취소-결제 경쟁 조건, 중복 콜백을 트랜잭션으로 처리한다. 미확정 철회 이후 결제 도착은 확정 금지하고 결제 취소/환불 보상 작업을 수행한다. PG 연결은 아직 없으며 현재 결제 성공/실패는 시연이다.

메이트 결제 유예시간, 취소·노쇼 시 수수료 반환, 수수료 세금·VAT 처리, 현금 지급 시점·분쟁 정책은 미확정이다. 이전 72/24시간 자동 환불률을 이 흐름에 적용하지 않는다. 출시 전 별도 확정하며 현재 UI는 현금 자동 환불을 약속하지 않는다. 과거 시연 예약은 정책 이력이므로 실거래로 취급하지 않는다.

닉네임 고유성

정책: Unicode NFKC 정규화, 전체 공백 제거, 소문자 변환한 canonical 값으로 중복 판단한다. 표시 이름은 앞뒤 공백을 제거하며 2~20자, 제어·숨은 포맷 문자 및 운영팀 사칭 이름은 거부한다. 자신의 기존 이름은 유지 가능하다. 변경 시 중복 확인 필수, 입력 변경 시 확인 상태 해제, 저장 직전 재조회한다.

시제품은 reeltrip-prototype-nicknames-v1 로컬 디렉터리와 샘플 메이트 미나/준으로 검사한다. traveler-demo는 단일 시연 소유자다. 실제 사용자 전체 중복, 멀티탭 경쟁 조건, 이름 확보는 보장하지 않는다. 로컬 확인은 서버 인가나 예약이 아니다.

실서비스: GET /api/nicknames/availability는 availability만 반환하고 계정 개인정보는 반환하지 않는다. PATCH /api/me/profile은 서버 세션의 user_id로 기존 소유권을 확인하고 같은 정규화 정책을 적용한다. DB nickname_canonical UNIQUE 제약과 트랜잭션으로 중복 재검사·새 이름 확보·기존 이름 반환을 원자적으로 수행한다. 중복 시 409 NICKNAME_TAKEN으로 반환하고 수정 상태를 유지한다. 사전 확인 성공은 이름 예약이 아니다. 탈퇴·변경 후 닉네임 재사용 유예 정책은 커뮤니티 출시 전 확정한다.

프로필과 진행 중인 여행

중복 내 장소/내 여행 통계 영역은 제거한다. 진행 중 요청 또는 예약만 마이에 이어보기로 표시한다. 프로필을 누르면 닉네임 2~20자와 JPG/PNG/WebP 1MB 이하 사진을 등록·수정·삭제한다. 기본값은 여행자와 기본 아이콘이다. profile.nickname/photo를 기존 로컬 상태에 저장하며 사진은 data URL이다. 실서비스는 계정 연결, 서버 업로드·파일 검증·삭제·보관 정책 구현이 필요하다.

마이·설정

마이는 프로필과 활동 바로가기만 표시한다. 우측 설정 아이콘으로 B-32 settings에 진입하며 언어·모드 전환, 도움말·약관, 데이터 내보내기·삭제를 제공한다. 설정은 고객/메이트 공통이며 언어 전환 후 설정에 머문다. 도움말·약관은 설정으로 복귀한다.

채팅 정책

  • 시작: 메이트가 매칭 수수료를 결제한 뒤 먼저 메시지를 보내면 여행자가 1:1 대화에 참여한다. 결제 전에는 양측 모두 메시지를 보낼 수 없다.
  • 이용 기간: 여행 마지막 날 24:00(Asia/Seoul, 다음 날 00:00)까지 대화할 수 있다. 중간 일정 완료로 종료하지 않는다.
  • 종료: 이용 기간 종료 또는 예약 철회·취소 완료 시 읽기 전용으로 전환한다. 취소 검토 중에는 이용 기간 내 대화를 허용한다.
  • 메시지: 텍스트 1~1,000자만 지원한다. 빈 메시지는 보낼 수 없으며 사진·파일 첨부는 지원하지 않는다.
  • 예약 조건: 만날 장소·시간을 확인하는 용도다. 채팅 합의만으로 선택한 일정·금액은 변경되지 않는다.
  • 확정: 예약은 메이트의 10% 매칭 수수료 결제 후 확정되며 메이트가 대화를 먼저 시작한다. 여행비는 현장에서 현금으로 직접 지급한다.

신고·차단 MVP

채팅방 더보기에서 사용자 신고·차단·해제를 제공한다. 신고는 사유 선택, 선택 상세(기타는 필수, 최대 1,000자)를 저장하며 같은 신고자의 같은 대화방 중복 신고를 막는다. 차단은 상대 ID 기준으로 다른 대화방에도 적용하고 양쪽 메시지 전송 및 미읽음 표시를 중단한다. 기존 대화와 예약 상태는 유지한다. 설정의 차단한 사용자에서 해제할 수 있다. 빈 목록은 차단 진입 경로를 안내하고, 목록이 있으면 사용자명·차단 중 상태·해제 버튼과 건수를 표시한다. 차단은 예약 취소가 아님을 안내한다. 해제 확인은 취소→차단 해제 순서로 제공하고 취소하면 목록으로 돌아간다. 해제 후 완료 안내와 갱신된 목록을 표시하며 마지막 사용자 해제 시 빈 상태로 전환한다. 상대방의 차단이나 채팅 종료 등 이용 조건으로 해제 후에도 전송이 제한될 수 있음을 확인창에 안내한다. 사용자·메이트 모두 상대를 신고·차단할 수 있다. 운영 웹의 문의·신고·차단에서 한국어·영어 앱의 신고자 역할·대상·사유·상세·시각·대화방 및 현재 차단 목록을 확인하고 새로고침할 수 있다. 차단 해제 후에도 신고 기록은 유지한다. 같은 브라우저·같은 출처의 로컬 저장소로 동작하며 외부 연동은 사용하지 않는다. 서버 연결 시 실제 사용자 ID, 인증·권한, 양방향 전송 차단 및 신고 처리 절차를 구현해야 한다.

현재는 실제 전송·서버 인증 없는 로컬 시제품이다. 역할별 읽음·미읽음과 새로고침 후 기록 유지를 시연한다. 서버 연결 시 참여자 권한·선택된 제안·예약 상태·종료 시각을 메시지 저장 트랜잭션에서 재검사해야 한다. 대화 보관 기간·삭제 기준·신고 및 제재 절차는 출시 전 별도 확정한다.

문의 접수와 Slack 알림 · MVP 개발 요건

2026-11-23 결정. 도움말의 직접 문의 작성에서 문의를 보내면 서버에 접수하고 운영팀 Slack 채널로 알린다. 사용자 흐름은 접수로 끝난다. 저장됨·처리 완료 전용 화면, 문의 이력, 저장 건수와 최근 상태는 제공하지 않는다. 처리 상태는 운영 웹에서만 관리한다.

  • 실서비스 버튼은 ‘문의 보내기’. 내용은 앞뒤 공백 제거 후 10~1,000자, 문의 유형은 허용 목록으로 서버에서 검증한다. 전송 중 중복 클릭을 막고 서버 접수 성공 시 ‘문의가 접수되었어요.’ 토스트를 잠시 보여준 뒤 빈 양식으로 돌아간다. 입력 오류·네트워크 오류·서버 오류는 내용을 유지하고 재시도를 허용한다.
  • 개발 API 계약: POST /api/support/tickets. 요청은 type, body, locale와 클라이언트가 생성한 Idempotency-Key. userId와 역할은 서버 세션에서 결정한다. 서버는 문의와 Slack 알림 작업을 하나의 트랜잭션으로 저장하고 201 {ticketId, status: 'received'}를 반환한다. 같은 사용자·키·동일 내용 재요청은 기존 접수 결과를 반환하고, 같은 키의 다른 내용은 409로 거절한다. 동일 제출 재시도에는 같은 키를 유지한다.
  • Slack 전송은 서버 작업자가 담당한다. 서버 비밀 설정 SUPPORT_SLACK_WEBHOOK_URL로 운영팀이 지정한 채널에 전송하며 브라우저·소스 저장소에 웹훅 주소를 노출하지 않는다. 알림은 문의 ID, 유형, 본문, 접수 시각(Asia/Seoul), 사용자 내부 ID·역할·언어, 권한 보호된 운영 문의 상세 링크로 구성한다. 사용자 입력은 일반 텍스트로 처리해 멘션 실행을 막고 인증 토큰·결제정보 등은 넣지 않는다.
  • 서버 접수와 Slack 전송 결과를 분리한다. Slack 장애가 나도 접수된 문의를 사용자에게 재제출시키지 않는다. 운영 웹에 알림 상태 pending/sent/failed와 재시도 횟수·마지막 오류를 표시한다. 일시 오류는 지수 지연으로 최대 5회 재시도하고, 최종 실패는 운영자가 재전송한다. 문의 ID로 작업 중복을 방지하되 응답 유실 시 외부 알림 중복 가능성은 같은 문의 ID로 식별한다.
  • 운영 준비: 수신 워크스페이스·채널 확정, 웹훅 비밀 설정, 서버 인증·접수 DB·작업자·운영 상세 링크·요청 빈도 제한 구현. 실제 테스트 문의는 별도 승인 후 발송한다. Slack 알림은 운영 수신용이며 Slack 답글을 앱으로 전달하는 기능은 MVP 범위 밖이다.
  • 인수 기준: 정상 제출 1건 접수 및 Slack 수신, 한영 문의 원문 보존, 연속 클릭·응답 유실 후 동일 키 재시도의 중복 접수 방지, 입력 오류·접수 실패 시 본문 유지, Slack 장애 후 재전송, 새로고침·처리 완료 후에도 사용자 상태 화면 미노출을 확인한다.

현재 시제품은 ‘문의 저장’과 외부 전송이 없다는 토스트로 브라우저 저장만 시연한다. 실제 API·DB·Slack 연결은 미구현이다. 기존 tickets 저장 키와 운영 웹 문의 상태는 유지한다.

제안 MVP 간소화 · 2026-11-23

요청 날짜·인원·기존 일정은 고정한다. 영어 동행은 하루 4시간, 메이트 입력은 일행 전체 금액이며 자유 여행에만 날짜별 코스를 입력한다. 요율·추가 인원 요금·변경 사유 편집을 제거한다. 유효한 제안 수정·중복 발행 금지, 만료 후에만 재발행 가능. 선택 시 제안 스냅샷 고정, 10% 수수료 결제 후 확정. 채팅으로 계약 조건은 변경되지 않는다. 서버 연동 시에도 동일 검증과 원자적 선택·중복 방지가 필요하다.

MVP 화면 범위 정리 · 2026-11-23

  • 외부 예약은 장소 카드의 외부 링크만 제공한다. 연결 상품이 있으면 해당 사이트로, 없으면 Google Maps 방문 정보로 이동한다. 예약·결제·변경·취소는 외부 사이트가 담당하며 앱 내 예약 기록 양식은 없다.
  • 일정은 날짜·장소 추가/삭제·순서 편집을 유지한다. 장소별 체류시간 편집·다른 날짜로 이동·날짜별 메모 입력은 제외한다. 구간별 직선거리와 도보 추정 시간, 출발·도착 좌표를 전달하는 Google Maps 길찾기를 유지한다.
  • 마이는 프로필·메이트 등록·설정 중심으로 축소한다. 중복 진행 요약과 예정된 일정 목록을 제거한다. 요청·예약은 메이트 제안함과 예약 상세에서 확인한다.
  • 메이트 가능 날짜 달력과 별도 수수료 내역은 제외한다. 메이트가 가능한 요청에 직접 제안하고 확정·취소 검토 중 예약과 기간이 겹치면 차단한다. 수수료 금액·결제·상태는 예약 상세에서 확인한다. 서버의 메이트별 동시 예약 검사는 별도 구현이 필요하다.
  • 여행 후기 작성·조회는 제외한다. 메이트 등록과 알림은 기존 기능을 유지한다.
  • 활성 화면은 35개이며 기존 B-* 번호를 재배정하지 않는다. B-21(review)·B-37(upcoming)은 booking, B-24(guide-calendar)는 guide-activity, B-25(guide-earnings)는 guide-fee로 기존 주소를 연결한다. 외부 예약 기록·메모·체류시간·후기·불가 날짜 등의 기존 로컬 저장값은 삭제하지 않는다.

시제품이며 실제 영상 분석·인증·결제·서버 동기화가 연결된 완료본이 아니다.

회원 탈퇴

마이 → 설정 → 회원 탈퇴. 여행자·메이트 공통으로 삭제 범위와 복구 불가 안내를 확인하고 필수 동의 후 탈퇴한다. 취소 → 탈퇴하기 순서이며 취소 시 데이터를 유지한다. 진행 중인 예약(메이트 확정 대기·확정·취소 검토 포함)은 완료 또는 취소 후 탈퇴한다. 현재 상태 및 한국어·영어 저장본의 예약 이력을 실행 직전에 재검사한다. 프로필·장소·여행·요청·제안·채팅·문의 및 메이트 신청·권한, 본인의 닉네임 점유를 삭제하고 게스트 홈으로 이동한다. 언어 설정과 타인의 닉네임 점유는 유지한다. 저장소 오류 시 완료로 표시하지 않는다. 브라우저 로컬 시제품이며 실제 인증 계정·서버 데이터 삭제는 미연동이다.

서버 연결 시 재인증, 사용자 소유권 검사, 예약·수수료 상태와 삭제의 원자적 처리, 전체 세션 무효화 및 개인정보 삭제·보관 정책을 구현해야 한다.

메이트 등록·승인

마이에서 메이트로 등록하기 → 전국 시·도 전체 또는 시·군·구 활동 지역 복수 선택(일반구가 있는 시는 구 단위, 제주는 제주시·서귀포시, 하위 시·군·구가 없는 세종은 전체)/영어·일본어·중국어·한국어 중 언어 1개 이상 복수 선택 → 필수 프로필 사진·직접 입력하는 활동 이름(사용자 닉네임과 메이트 활동 이름의 통합 중복 검사, 2~20자)·통합 자기소개(10~1,000자) → 비공개 휴대폰 번호·6자리 문자 인증 UI(시연용 123456, 실제 발송 없음, 유효시간 3분, 재전송 간격 30초, 5회 실패 제한) → 입력 확인·필수 동의 → 심사 요청. 활동 지역 선택은 하단 바텀시트로 제공하며 제목·시도 선택과 선택 요약·완료 버튼은 고정하고 지역 목록만 스크롤한다. 지역 버튼은 기본 4열, 360px 미만에서는 3열이며 내용을 약 90% 크기로 압축하고 최소 40px 터치 영역을 유지한다. 단계 진행률·이전·닫기·자동 임시 저장을 제공한다. 필수 사진은 JPG/PNG/WebP 1MB 이하로 미리보기·교체·삭제하며 브라우저에 저장한다. 동네와의 인연·걷는 속도/휴식·가능한 도움은 자기소개 한 영역에 자유롭게 작성하며 기존 개별 입력값은 빈 줄로 합쳐 보존한다. 관련 경험·자격 입력란은 제공하지 않는다. 공개 미리보기에는 본인 작성·미검증을 표시하고 연락처을 제외한다. 실제 운영의 확인 표시는 항목별 근거 종류·검토자·확인 일시와 유효기간 기록이 있어야 하며, 등록 승인 자체로 인증 배지를 부여하지 않는다. 완료 동행·후기는 실제 완료 예약과 연결된 기록만 집계한다. 시제품에는 확인 및 동행 기록 없음으로 표시한다. 자택 주소와 실제 증빙은 시제품에서 수집하지 않는다.

draft → pending → approved 또는 needs_info/rejected. 보완 요청과 거절은 사유 필수이며, 신청자는 수정 후 pending으로 재제출할 수 있다. 심사 중에는 제출 내용을 읽기만 가능하다. 승인 후에만 메이트 모드 전환과 활동을 허용한다. 메이트 마이의 프로필 편집에서 사진·활동 이름·자기소개를, 활동 정보 수정에서 분야·복수 지역·언어를 변경한다. 저장 시 반영하고 취소 시 폐기하며, 이름 변경은 중복 확인이 필요하다. 승인 상태와 비공개 연락처·심사 정보는 유지한다. 여행자 기능은 계속 이용 가능하다. 신청 시 결제하지 않으며 여행자 선택 후 10% 매칭 수수료 결제 → 예약 확정, 여행비 현장 현금 직접 지급 규칙을 유지한다.

운영 웹의 메이트 등록 심사에서 신청서·비공개 연락처을 검토하고 확인 체크 후 승인한다. 실제 운영에서는 본인 확인·자격 진위·계약 검증 기록이 있어야 승인 가능하다. 관련 자격 요건과 심사 소요시간은 출시 전 운영 정책으로 확정한다. 공개 프로필에는 연락처·증빙·심사 사유를 포함하지 않는다.

현재는 reeltrip-mate-application-v1에 하나의 시연 신청서를 저장하고 같은 출처·브라우저의 앱/운영 웹에서 공유한다. 한국어·영어 화면은 같은 신청서를 사용한다. 승인 상태를 기존 reeltrip-prototype-access-v1 권한에 반영한다. 활동 이름은 랜덤 부여하지 않으며 단계 진행과 제출 시 통합 목록을 재검사한다. 현재 중복 검사는 동일 브라우저의 시연 데이터에 한정되며 실서비스에서는 사용자 닉네임과 메이트 이름을 통합한 서버 고유 제약이 필요하다. 실제 사용자별 DB·인증·실제 SMS 발송 및 서버 검증·서류 업로드·알림·다중 사용자 처리는 미구현이다. 실제 승인 API는 관리자 권한·pending 상태·필수 검증·신청 버전을 서버에서 확인하고 역할 부여와 심사 로그를 원자적으로 저장해야 한다. 모든 메이트 활동 API는 서버에서 승인 상태를 검사해야 한다.

공개 여행 요청과 메이트 탐색 정책

2026-11-23 결정. 여행자가 명시적으로 제안 받기에 동의한 요청만 모든 승인 메이트에게 공개한다. 작성 중인 여행과 개인 장소 보관함은 비공개다. 초기에는 지역 불일치를 이유로 열람을 제한하지 않으며 요청별 전체 제안 수 상한을 두지 않는다. 동일 메이트의 유효한 제안 중복 제한은 유지한다.

  • 흐름: 여행자가 공개 항목 확인·동의 → 승인 메이트가 여행 찾기에서 탐색 → 복수 메이트의 일정·가격 제안 → 여행자 비교·선택 → 신규 제안 접수 중단 → 선택 메이트의 10% 수수료 결제 → 확정. 여행비는 현장 현금 직접 지급한다.
  • 공개 항목: 날짜·지역·인원·안내 언어·공개 방문 장소·요청사항. 연락처, 정확한 숙소 주소, 개인 여행 제목, 계정 ID, 비공개 메모는 공개 응답에서 제외한다. 자유 입력에 개인정보를 적지 않도록 사전 안내하고 서버에서 검출·수정 요청을 처리한다. 클라이언트에서 숨기는 것만으로 보호했다고 간주하지 않는다.
  • 기본 정렬: 활동 지역과 전 일정 가능 여부 모두 일치 → 날짜 가능 → 지역 일치 → 최신 공개 순 → 요청 ID 순. 지역 미입력·인식 불가 요청도 목록에 남긴다. 실서비스는 표준 지역 코드로 매칭하고 날짜는 한국 시간 기준으로 예약 충돌과 메이트 휴무를 확인한다. 지역·날짜 필터는 선택사항이며 초기 기본값은 전체 공개 요청이다.
  • 상태: requested/quoted만 탐색에 노출. 여행자 선택·철회·마감 시 목록에서 제외하고 제출 시 상태를 재검사한다. 선택 대기 만료로 요청이 다시 열리면 재노출한다. 선택과 제안 제출 경합은 서버 트랜잭션으로 처리한다.
  • 성장 단계: 우선 지역·날짜·언어 적합도에 따라 노출 순서와 알림 대상을 좁힌다. 요청당 제안 수, 첫 제안 도착 시간, 무제안 요청 비율을 관찰한 뒤 제안 수 상한 또는 적합 메이트 우선 공개·점진 확대를 도입한다. 회원 수만으로 제한하지 않으며 수치 기준은 운영 데이터로 결정한다. 초기 자동 푸시·독점 배정은 제공하지 않는다.

서버 개발 계약: 공개 요청 조회·상세·제안 API 모두 승인된 메이트 권한을 서버에서 검사한다. 목록과 상세는 허용 필드만 반환하고 검색·페이지네이션에도 같은 공개 상태 조건을 적용한다. 여행자 본인만 공개·철회·선택 가능하다. 비승인·정지 계정의 조회 및 제출을 거절한다. 개인 여행 원본과 공개 스냅샷을 분리하고 공개 시점·동의 버전·종료 사유를 기록한다.

현재 구현: 로컬 활성 요청 1건과 기존 저장 키를 유지한다. 공개 동의 안내, 승인 메이트 화면 접근, 공개 상태 필터, 지역 문자열·예약 충돌 기반 정렬을 시연한다. 요청 자유문은 목록에 노출하지 않는다. 실제 다중 사용자 피드·표준 지역 매칭·휴무 관리·개인정보 검출·서버 권한·알림은 미연결이며 완료본으로 표시하지 않는다.

여행 지도 핀 누락 · 개발 인계

실서비스 요구사항: 선택한 날짜의 일정에 포함된 위치 확인 완료 장소는 모두 지도에 표시한다. 성수 3곳 뒤에 4번 N서울타워를 추가하면 남산까지 포함하도록 지도 범위를 자동 조절하고, 목록과 같은 4번 핀을 표시해야 한다.

현재 시제품에서 4번이 보이지 않는 이유

2026-11-23 확인. 화면 탐색의 기본 미리보기는 src/frontend/preview-map-config.js에서 review 모드로 설정한다. src/assets/app.js의 reviewMapImage()는 성수동 고정 지도 캡처 위에 핀을 겹쳐 그리며, reviewPosition()은 캡처 범위 밖 좌표를 null로 반환한다. N서울타워는 좌표가 있지만 남산에 있어 범위 밖으로 제외된다. 이는 ‘핀은 3개까지만 표시’라는 제품 정책이나 일정 추가 실패가 아니라 고정 이미지 미리보기의 한계다. 캡처 안에 임의로 4번 핀을 배치해서 해결하지 않는다.

실제 지도 구현 기준

  • 실제 지도에서는 선택 날짜의 전체 일정 좌표로 bounds를 계산한다. 최초 진입·날짜 전환·장소 추가/삭제 시 모든 핀이 보이도록 조정하며 헤더·일정 시트에 핀이 가리지 않도록 여백을 반영한다. 한 장소는 적정 확대 수준으로 중심 이동하고, 빈 일정은 빈 상태를 표시한다.
  • 목록의 방문 순서와 핀 번호를 동일하게 유지한다. 위치 미확인 장소를 제외하더라도 나머지 핀 번호를 다시 매기지 않는다. 순서 변경 시 번호도 함께 갱신한다.
  • 실제 지도 전환만으로 기존 예시 장소가 모두 표시되지는 않는다. 현재 pinEligible()은 Google placeId와 유효 좌표가 있고 demoCoordinates/demoPreview가 없는 장소만 허용한다. catalog.js의 N서울타워는 demoCoordinates:true인 예시다. 서비스에서는 실제 장소 검색·선택으로 위치를 확인한 데이터를 사용하고, 예시 플래그만 지워 위치 검증을 우회하지 않는다.
  • 좌표 누락·위치 미확인 장소는 일정 목록에 유지하고 ‘위치 확인 필요’ 안내와 장소 재선택 경로를 제공한다. 지도 연결 실패 시에도 목록을 유지하고 오류·재시도를 안내한다. 고정 이미지가 전체 장소를 표시하는 실제 지도인 것처럼 보이게 하지 않는다.
  • 직선 연결선은 방문 순서 표시이며 실제 도보 경로가 아니다. 실제 경로 데이터 연동 전에는 도보 경로로 안내하지 않는다.

인수 확인 항목

  • 실제 위치 확인을 마친 성수 3곳과 N서울타워로 일정 구성 → 지도에 1~4번이 모두 보이고 4번은 남산 위치에 표시된다.
  • 4번 추가/삭제, 순서 변경, 날짜 전환, 저장 후 재진입 → 현재 날짜 목록과 핀·번호·지도 범위가 일치한다.
  • 중간 장소의 좌표 누락 → 해당 목록 항목에 확인 안내가 보이며 이후 장소 번호가 당겨지지 않는다.
  • 장소 0개/1개, 지도 로딩 실패, 한국어/영어 및 모바일 일정 시트가 열린 상태를 확인한다.

이 항목은 개발 요구사항이며 현재 실제 지도 연동과 인수 검증을 완료했다는 의미가 아니다.
